## 1. Introduction
Network Intrusion Detection Systems (NIDS) are designed to analyze and identify malicious traffic in order to identify potentially malicious activity by detecting and inspecting patterns associated with known attacks. This project aims to investigate the effectiveness and the limitations of a signature-based approach, employing Suricata, an open-source network analysis and threat detection software. Our analysis focuses toward HTTP traffic and a selected set of malicious network behaviors.
The effectiveness of the proposed rules is assessed by comparing the alerts generated by Suricata with ground truth of the analysed traffic, allowing true positives, true negatives, false positives, and false negatives to be identified.
Particular attention is given to slow scanning and IP fragmentation, two scenarios that may challenge signature-based detection. The analysis aims to evaluate the ability of custom signature-based rules to distinguish malicious from legitimate traffic and to investigate the trade-offs and limitations introduced by rule refinement.

### 1.1 Network Intrusion Detection
The Network Intrusion Detection System (NIDS) is a security mechanism designed to monitor network traffic and devices for known or potential malicious activity, suspicious behaviours or security policy violations [1].
The main purpose of an IDS is to automate threat detection within a network, alerting administrators of suspicious activities.

### 1.2 Detection models
Based on the chosen detection model, IDSs can generally be classified in three categories:
- Signature-based detection identifies malicious activity by comparing network traffic against signatures and rules associated with common and known attack patterns. However, its ability to detect previously unseen attacks is limited by the signatures currently available to the system.
- Anomaly-based detection identifies potentially malicious activity by detecting deviations from an established model of normal network behaviour. This approach can potentially detect either known and unknown attacks, but at the same time it can easily generate false positive from abnormal legitimate behaviours.
- Hybrid-based detection [2] combines signature-based and anomaly-based detection mechanisms. This approach can provide a broader detection capabilities, but generally introduces greater complexity with using a single detection methodology.

## 2. Background
For this project, we use Suricata [3], an open-source Network Intrusion Detection and Prevention System (NIDS/NIPS), widely used for real-time network traffic analysis. Suricata supports rule-based inspection of network traffic and provides mechanisms for detecting predefined patterns associated with malicious activity.

Suricata was selected primarily because it supports custom detection rules, allowing us to investigate the effectiveness and limitations of a relatively simple signature-based approach.

### 2.1 HTTP Traffic
We focused on on HTTP traffic, with custom rules targeting specific begaviours such as suspicious, such as port scanning, suspicious HTTP requests, repeated logins and unusual inputs.

### 2.2 Slow Scanning and IP Fragmentation
The analysis also considers two scenarios that may challenge signature-based detection: slow scanning and IP fragmentation. These scenarios allow us to investigate how changes in the timing or structure of network traffic can affect the ability of predefined rules to detect malicious activity.
The overall objective is to evaluate the trade-off between detection capability and false alarms, measuring, for instance, true positive, false positives and false negatives under both benign and malicious traffic conditions.

## 3. Threat Model and Scope
### 3.1 Defensive Scenario
The considered scenario consists of a monitored network in which Suricata is deployed to observe and report potentially suspicious traffic. Suricata observes the traffic exchanged between several hosts (including the attacker) and a monitored HTTP server and generates alerts when the configured detection rules match the observed traffic. The primary objective is detection rather than prevention. The project evaluates whether specific malicious activities can be identified from the observed network traffic.

The experimental environment is based on pre-recorded network traffic obtained from public datasets [4]. These datasets provide labelled traffic that can be used as ground truth for evaluating the detection results.

### 3.2 Attacker Capabilities
We assume an attacker capable of generating and controlling network traffic directed towards the monitored server. The attacker is able to perform different type of network intrusion, for instance: port scanning, malicious HTTP requests and repeated authentication attempts. The attacker can modify the characteristics of the generated traffic in order to deceive the detection mechanisms.

The attacker is not assumed to have control over or be able to compromise the monitoring infrastructure or the monitored server.

### 3.3 Assumptions
The analysis assumes that Suricata is able to observe the relevant network traffic. The experiments focus on HTTP rather than encrypted HTTPS traffic, allowing the detection rules to inspect the application-layer characteristics of HTTP requests.

Since the experiments are conducted in a controlled environment, the ground truth of each traffic sample is known in advance and can be used to evaluate the effectiveness of the selected rule set.

### 3.4 Out-of-Scope Scenarios
The scope of the project is limited to a network-based, signature-based intrusion detection using Suricata. Therefore, the following detections are not addressed or performed in any way: host-based intrusion detection and malware analysis.

## 10. Individual contributions

### Fabrizio Sclosa
I worked mainly on the project datasets, the implementation and experimentation of the evaluation scripts, and parts of the Suricata detection rules, which together make up the experimental side of the project. In addition, I worked on setting up the environment and documenting the repository structure and usage.

At first, I searched for and selected possible datasets to work with (both for developing the rules and for testing them). I opted for Edge-IIoTset as the training set because of its broad range of attack patterns and benign traffic, and CIC-IDS-2017 as the test set (using the improved CSV flows along with the original PCAPs). During the selection process, I extensively tested [UNSW-NB15](https://research.unsw.edu.au/projects/unsw-nb15-dataset) as well, but at the end excluded it, since it was out of scope.

Secondly, I built the evaluation scripts, `evaluate_training.py` and `evaluate_test.py`. They serve the same purpose but compare `eve.json` against the ground truth CSVs in different ways: the former matches by the pair timestamp + pcap_cnt, the latter by packet flow using the 5-tuple (IPs, ports and protocol). This difference is due to the fact that the two ground-truth CSVs have different structures and labelling criteria. Both scripts report the confusion matrix of the Suricata analysis, which includes true positives, false negatives, false positives, true negatives, recall, precision, false positive rate, true negative rate, accuracy and F1. These scripts made it possible to find a proper matching mechanism between the Suricata alerts and the ground truth, and also allowed a quick performance overview of the tested rules.

Along with this experimental part of the project, I adapted and fixed the `run.sh` script to allow centralized control of the Python scripts, Suricata and the datasets, which made the repository easier to use. Finally, I prepared and configured the setup, the usage documentation and the repository layout described in the `README.md`.
